## 1. 목표·이유

LLM 서빙은 지연이 튀었을 때 원인이 여러 층에 걸쳐 있다 — 트래픽, 요청 모양(긴 입력·긴 출력),
KV 캐시 용량, 같은 GPU를 쓰는 다른 작업, 호스트 CPU. 대시보드에는 수십 개의 메트릭이 같이 움직이고,
그중 무엇이 원인이고 무엇이 증상인지는 보이지 않는다.

기존 작업은 "빠르게 서빙하기"(`vllm-serving-bench`: 처리량 154배, `triton-inference-bench`)와
"요청 단위 추적"(Langfuse)까지였다. **서빙이 느려졌을 때 그걸 언제 알아채고 원인을 어떻게 좁히는지**는 다루지 않았다.
이 저장소는 그 빈칸 — GPU 추론 워크로드의 모니터링·이상 탐지·장애 원인 분석 — 을 직접 재현해서 잰다.

## 2. 상품성 — 누가 왜 쓰나

- **LLM 서비스 운영팀**: 지연 SLO 위반 경보가 울렸을 때 "스케일아웃할 일인가(트래픽), 요청 정책을 바꿀 일인가(긴 입력),
  노드를 비울 일인가(GPU 경합)"는 대응이 전부 다르다. 원인을 틀리면 비용만 쓰고 장애는 계속된다.
- **APM·AIOps 제품**: 메트릭 이상 탐지와 원인 추천은 모니터링 제품의 핵심 기능이다. 여기서는 정답 원인을 아는 장애를
  직접 만들어 넣었기 때문에, "원인 추천이 몇 번 맞는가"를 추정이 아니라 정답 대조로 잰다.

## 3. 설계와 채용 근거

### 실험 장치

| 구성 | 내용 | 이유 |
|---|---|---|
| 서버 | vLLM 0.26, Qwen2.5-1.5B, `--max-num-seqs 64`, `--max-model-len 4096` | 기존 벤치와 같은 모델·GPU라 수치를 이어서 읽을 수 있다 |
| KV 용량 | `--num-gpu-blocks-override 2048` (= 32,768토큰) | 1.5B 모델에 16GB를 다 주면 KV 여유가 너무 커서(12,417블록) 긴 입력 장애가 재현되지 않는다. **큰 모델을 작은 GPU에 올린 상황의 용량 제약을 인위적으로 만든 것**이다 |
| 평상시 부하 | 사용자 8명, 입력 약 200단어·출력 128토큰, 생각 시간 평균 0.2초(지수분포) | 폐쇄 루프라 서버가 느려지면 도착률도 줄어든다 — 실제 사용자와 같은 동작 |
| 수집 | 1초마다 vLLM `/metrics`(60여 종), NVML(GPU 사용률·전력·클럭·메모리), 호스트·vLLM 프로세스 CPU, 클라이언트 지연 p50/p90·TTFT | Prometheus가 긁어 가는 것과 같은 원천을 직접 긁었다. 매초 flush해서 측정이 죽어도 남는다 |

### 주입한 장애 5종 (각 60초, 회복 60초)

| 장애 | 주입 방법 | 현실의 대응 사례 |
|---|---|---|
| `surge` | 동시 사용자 8명에서 64명으로 | 트래픽 급증 → 스케일아웃 |
| `longctx` | 약 3,000토큰 입력 12개 동시 추가 | 긴 문서 RAG 요청 폭주 → 입력 길이 제한·전용 풀 분리 |
| `longout` | 1,500토큰 출력 16개 동시 추가 | 긴 생성 요청 → max_tokens 정책 |
| `gpu_hog` | 같은 GPU에서 fp16 4096×4096 행렬곱 무한 루프 | 학습·배치 잡이 추론 GPU에 끼어듦 → 노드 격리 |
| `cpu_hog` | 호스트 코어 수 × 2개 busy-loop 프로세스 | 같은 노드의 CPU 작업 → 토크나이저·스케줄러 지연 |

### dev / test 분리

같은 절차를 시드만 바꿔 두 번 돌렸다(장애 5종 × 4회 = 20건, 순서 무작위).
**임계값·규칙·분류기는 dev에서만 정하고 고정한 뒤 test에서 한 번 평가**했다.

- dev(시드 1, 09-28): 16번째 장애 뒤 WSL VM이 내려가 **15건(5종 × 3회, 종류별 균형)**에서 끝났다. 매초 flush 덕에 그때까지의 1,888행이 남아 있어 그대로 dev로 썼다.
- test(시드 2, 09-30): 20건 전부 완주, 2,492행.

## 4. 방법별 비교 — 무엇이 왜 갈렸나

### 탐지

- **고정 SLO(D1)는 긴 출력을 놓친다.** 클라이언트 지연은 요청이 *끝나야* 기록되는데, 1,500토큰 출력 요청은
  장애 60초 안에 거의 끝나지 않는다. 기존 사용자 요청이 느려진 것만으로는 1.5초를 넘기지 못한 경우가 2/4였다.
  지연 최대 55초도 같은 이유다.
- **분위수 임계(D2)는 dev에선 완벽하고 test에서 오경보를 냈다.** 두 실행의 정상 기준선이 16% 달랐다.
  단일 지연 신호에 임계를 촘촘히 붙일수록 기준선 이동에 약해진다.
- **이동 z-score(D3)는 늦다.** 직전 120초 창에 앞선 장애의 회복 구간이 섞여 표준편차가 부풀기 때문에
  (장애 간격 60초라 창이 거의 항상 이전 장애를 포함한다) 오경보 0을 만들려면 k를 0.75까지 낮춰야 했고, 그래도 중앙 9.8초.
  이건 장애 밀도가 현실보다 높은 실험 설계의 영향이 섞여 있다.
- **IsolationForest(D4)가 유일하게 재현율 1.00·오경보 0·중앙 2.8초를 같이 냈다.** 지연 하나가 아니라
  처리량·KV·CPU·전력이 같이 어긋나는 걸 보기 때문에, 한 신호의 기준선 이동에 덜 흔들린다.

### 원인 분석

- **"가장 크게 튄 메트릭"은 증상을 원인으로 읽는다.** 긴 출력은 시퀀스가 오래 살아남아 KV 사용률이 9배로 오른다.
  대시보드에서 KV가 가장 붉으니 "긴 입력"으로 읽는다. 둘을 가르는 건 **요청당 입력 토큰**(longctx 15.8배, longout 1.10배)이다.
- **규칙 v1은 GPU 점유를 CPU 포화로 읽었다**(아래 5절).
- **분류기가 1.00인 건 "RCA가 풀렸다"가 아니다.** 원인을 하나씩, 깨끗하게, 같은 주입기로 넣었으니 다섯 장애가 특징 공간에서 잘 갈린다는 뜻이다.
  규칙 v2도 1.00이라 이 조건에선 모델이 규칙보다 나을 근거가 없다. 규칙은 틀렸을 때 **왜 틀렸는지 읽을 수 있다**는 게 차이다.

## 5. 교체 기록

| 무엇 | 교체 전 | 교체 후 | 근거 |
|---|---|---|---|
| RCA 규칙 | v1: `host_cpu z > 5`이면 cpu_hog | v2: `host_cpu z > 30` 또는 `vllm_cpu z < -5` | dev gpu_hog 3/3 오판. GPU 점유 프로세스도 커널을 쉬지 않고 제출하느라 코어 하나를 태워 host_cpu z가 6이 된다. 진짜 CPU 포화는 z 78이고 vLLM CPU가 줄어든다(-9.9). test gpu_hog 0/4 → 4/4 |
| z-score k 탐색 격자 | 2.0부터 | 0.5부터 | 격자 하한 2.0에서 이미 오경보 0이라 더 낮은 k를 보지 못했다. dev 재현율 0.53 → 0.80 |

v1은 비교를 위해 코드에 그대로 남겼다(`rca_rules`). v2는 dev만 보고 고친 뒤 test를 돌렸다.

## 6. 에러·함정 기록

- **dev 측정이 16번째 장애에서 끊겼다.** 로그에 예외 없이 WSL VM이 내려갔다(다음 기동 시 `uptime` 0분).
  매초 flush 설계라 1,888행이 남았고, 마침 3회차까지가 종류별로 균형이라 재측정 없이 dev로 썼다. test는 `Start-Process`로 분리 기동해 완주.
- **히스토그램 평균을 그대로 z-score에 넣으면 폭발한다.** 대기·선점 계수는 평상시 0이라 표준편차도 0 → z가 수십만.
  분모 하한(평균의 5%, 대기·선점은 1.0)을 뒀다.
- **KV 여유가 너무 크면 장애가 재현되지 않는다.** 1.5B 모델에 16GB를 주면 12,417블록이 잡혀 긴 입력 12개로도 대기가 생기지 않았다.
  `--num-gpu-blocks-override 2048`로 용량 제약을 인위적으로 만들었다(설계표에 명시).
- **메트릭 수집 행이 시간보다 적다.** dev 1,977초에 1,888행 — 스크레이프가 1초를 넘긴 순간 다음 틱을 건너뛴다. 분석은 행의 `t`로 정렬하므로 결과엔 영향 없다.

## 정직한 범위

- 단일 GPU·단일 모델(1.5B)·KV를 인위적으로 줄인 설정. 장애는 한 번에 하나씩, 60초씩 깨끗하게 넣었다 — 실제 장애는 겹치고 서서히 온다.
- test는 장애 20건(종류당 4건). 1.00은 "20건 전부 맞음"이지 일반 정확도가 아니다.
- 정상 구간이 짧다(test 11분). 오경보율을 시간당으로 환산하지 않고 횟수로 적었다.
- 로그·트레이스는 쓰지 않았다 — 메트릭만.
